# 架构说明

本文档由代码逆向整理（仓库 `E:\repo\att`），所有结论均给出文件路径与行号。**代码与既有描述冲突时以代码为准**，冲突点单独标注。

## 1. 总览：三层与「谁启动谁」

| 层 | 目录 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| Electron 主进程 | `electron/` | 应用生命周期、窗口、托盘、剪贴板监控、全局热键/静音代理、**拉起并监控 Python 后端** | 不做业务逻辑，不直接读写 `data/` |
| Vue 渲染进程 | `src/` | UI、录音采集（MediaRecorder / AudioWorklet）、状态展示；经 HTTP + WebSocket 直连后端 | 不经过 IPC 转发业务请求（`src/api/client.js:1-3`） |
| FastAPI 后端 | `app/` | 转写编排、LLM 优化、JSON 持久化、ASR/LLM provider 装配 | 不启动 Electron，不管理窗口 |

### 1.1 启动链路

```
electron/main.js:584  app.whenReady()
  ├─ startDesktopAgent()        main.js:232   （失败不阻断，仅缓存错误事件）
  ├─ startBackend()             main.js:200   → electron/python/manager.js
```

### 1.2 两个 PythonManager 的分工

两个文件都 `module.exports = { PythonManager }`，`electron/main.js:4-5` 用别名区分：

| 文件 | main.js 中的别名 | 实际用途 |
| --- | --- | --- |
| `electron/python/manager.js` | `PythonManager` | **真正拉起业务后端**（`main.js:201`） |
| `electron/python/runtime-manager.js` | `PythonRuntimeManager` | 只当「Python 路径解析 + 子进程 spawn 工具」用（`main.js:234-241`） |

**代码与直觉不符**：`runtime-manager.js` 自身也有完整的 `start()` / `stop()` / `waitForReady()`（`runtime-manager.js:262-338`），但全仓只调用了 `getPythonPath()` / `getRuntimeRoot()` / `spawnBackendProcess()`（`main.js:234-241`）——**它的 `start()` 在生产路径上从未被调用**。

### 1.3 端口如何分配

`electron/python/manager.js`：

1. `getPreferredBackendPort()`：`ATT_BACKEND_PORT` → `PORT` → `8000`（`:85-89`）。
2. 先探测该端口是否已有健康后端（`healthCheck()` 打 `GET /api/health`，`:256-281`）。**有则直接复用**并置 `externalBackend = true`（`:295-302`），退出时不会去 kill 别人的进程（`:387-392`）。
3. `ATT_REQUIRE_EXISTING_BACKEND=1` 且探测失败 → 直接抛错（`:91-102, 307-313`）；否则 `findAvailablePort(preferred, 100)` 向后找可用端口（`:207-215`）。
4. 启动后 `waitForReady()` 轮询 `/api/health`，500ms 一次、默认上限 30s（`:235-251`），超时则 `stop()` 并抛错。

`runtime-manager.js` 的差异：固定从 `8000` 起找端口（`:152-161`）；启动超时读 `BACKEND_START_TIMEOUT_MS`（默认 120s，`:226-235`）；健康探测超时 2s（`:244`）；Windows 上 `spawn` 遇 `EPERM` 会退回 `cmd.exe /d /s /c` 重试（`:206-224`）。

**注意**：两处都会注入 `PORT` 环境变量，但 `app/config.py` 的 `Settings` **没有 `port` 字段**，后端实际只认 uvicorn 的 `--port` 参数；`PORT` 对后端是无效变量（`docker-compose.yml:98` 同此）。打包态才注入 `DATA_DIR=<userData>/data`（`manager.js:63-83, 333-338`），开发态保持仓库内 `data/`。

## 5. 持久化与并发约束

### 5.1 `json_store.py`：原子写 + 宽容读

- 唯一落盘入口 `write_json_atomic()`：**同目录 `<name>.tmp` → `fsync` → `os.replace()`**（`json_store.py:85-118`）；任何一步失败都清理临时文件，目标文件要么是旧内容要么是完整新内容。异步版把落盘丢线程池（`:121-130`）。
- 读取分两档：`read_json` 严格（非法即抛）、`read_json_lenient` 宽容（缺失/损坏一律返回默认值，`:144-158`）；`ensure_dict()` 收敛「顶层不是对象」的坏形状（`:173-191`）。
- 锁按**规范化资源路径**划分：异步用 `asyncio.Lock`（按事件循环弱引用缓存），同步用 `threading.RLock`（`:28-82`）。

### 5.2 `writer_lock.py`：单写者锁

锁文件 `data/.writer.lock`（`writer_lock.py:26`）。

| 机制 | 参数/行为 |
| --- | --- |
| 心跳刷新 | 后台线程，每 15s 一次（`:32, 376-391`） |
| 陈旧判定 | 心跳超过 60s，或同机 PID 已不存在（`:29, 356-366`） |
| PID 探活 | POSIX 用 `os.kill(pid, 0)`；**Windows 用 `OpenProcess` + `GetExitCodeProcess`**，因为 `os.kill(pid,0)` 在 Windows 会真的结束进程（`:107-127`） |
| 冲突行为 | **抛中文 `RuntimeError`，直接拒绝启动**（`:275, 368-374`），不做「容错继续跑」 |
| 旁路 | `ATT_ALLOW_MULTI_WRITER=1` 跳过约束且不写锁文件（`:76-80, 259-269`） |

### 5.3 为什么 JSON 存储不允许两个后端进程同时写

`data/` 是唯一真相源，没有数据库事务或行锁；两个进程各自持有内存态、各自做「读-改-写」，最终 `os.replace` 会互相覆盖 → **静默丢数据**（`writer_lock.py:1-9`）。设计上把这种风险转换成显式的启动失败，覆盖两个真实场景：原生应用 + Docker 容器共用仓库内 `data/`（`docker-compose.yml:30`），以及误开两个后端实例。

### 5.4 `record_index.py`

`data/records/*.json` 是源真相，`data/.index/records.json` 是可随时删除的**派生清单**（`record_index.py:1-16`）。刷新靠 `os.scandir` + `(mtime_ns, size)` 比对做增量；API 写入路径 write-through `invalidate()`；索引自身出错由 `records_service` 吞掉并回落全目录扫描，保证 `GET /api/records` 不 500（`records_service.py:1-11`）。

## 9. 已知架构缺口（如实记录）

**9.1 统一浮层没有任何可用触发入口。** IPC 接收端存在（`electron/main.js:540-552`），窗口管理器实现完整（`electron/overlay/index.js:258-304`），preload 暴露了方法（`electron/preload.js:36-37`），`useElectron.js` 也包了 `overlay.openClipboard/openSelection`（`:117-127`）。**但渲染侧没有任何组件调用它们**——全仓检索只命中 `useElectron.js` 自身的定义。唯一可能触达的路径是 `clipboardOverlay.show/toggle`（`:104-115`），它只被 `App.vue:127-134` 的 WebSocket 分支调用，而该分支 (a) 在 Electron 运行时被显式忽略（`App.vue:104-111`）、(b) 依赖服务端下发 `clipboard_overlay_command`，而 `app/` 中**没有任何代码产生该消息**。托盘菜单也没有对应项（`electron/tray/index.js:129-143` 只有设置与退出）。结论：浮层代码与测试（`tests/test_unified_overlay_manager.js`）都在，但**入口链路是断的**。

**9.2 多段录音最后一片上传失败会卡住。** `createRecorder()` 的 `recorder.onstop` 直接 `await onStop(blob)`，**没有 try/catch**（`useRecorder.js:599-602`）；多段路径的 `onStop` 回调在 `await uploadRealtimeSegment(...)`（`:1099`）之后才调用 `maybeFinalizeRealtimeSession()`（`:1115`）；而 `uploadRealtimeSegment()` 只有 `try/finally`、**没有 catch**（`:959-973`），失败时异常向上抛。后果：最后一片上传失败 → 异常在 `await` 处中断回调 → 第 1115 行的收尾永远不执行 → 会话不合并、`livePhase` 停在 `segment-processing`、`isTranscribing` 不复位。

**9.3 全局 WebSocket 的重连能力有限。**（**此点与常见描述不符，以代码为准**）`src/composables/useWebSocket.js` **已有**自动重连：`onclose` 时 `scheduleGlobalReconnect()`，固定 3s 后重连（`:36-46, 111-116`），并带 30s 心跳（`:104-109`）。实际缺口收窄为：重连**固定 3s、无指数退避、无次数上限**，后端长时间不可用时会持续打点；`onerror` 本身不触发重连，依赖随后的 `onclose`（`:48-51`）；`useWebSocket()` 旧入口（`:159-173`）全仓无调用方，属死代码，主窗口用的是 `useGlobalWebSocket()`（`App.vue:59`）。

**9.4 LLM provider 未设置请求超时。** 多 provider 路径构造 `AsyncOpenAI` / `AsyncAnthropic` 时**只传 api_key 与 base_url，没有 `timeout`**（`app/llm/providers/openai.py:17-20`；claude 为 `AsyncAnthropic`，deepseek/doubao/qwen 同为 `AsyncOpenAI`，均在各自文件第 17 行），因此使用 SDK 默认超时（600s）。对照：旧 DeepSeek 直连路径的 `TextOptimizer` **有** 60s 超时（`app/llm/optimizer.py:164-171`）并配 `stop_after_attempt(3)` 重试（`:179-184`）。影响：设置页「测试连接」与 AI 动作（`app/ai_actions/service.py` 经 `LLMGateway`）在服务端无响应时会长时间挂起。
