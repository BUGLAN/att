### 2.2 不协调的根因：三个"分裂"

**分裂 ①：三套金色并存（最致命的视觉问题）**

| 变量 | 值 | 位置 |
| --- | --- | --- |
| `--accent` | `#c9a227`（暗金） | `src/styles/main.css:26` |
| `--overlay-accent` / `--floating-accent` | `#ffc557`（亮金） | `src/styles/clipboard-overlay.css:9`、`src/styles/floating.css:6` |
| 划词面板橙金 | `#f3b460` | `src/components/overlay/SelectionPanel.vue:339` |

而 `SelectionPanel` 与 `ClipboardPanel` **同处一个窗口**（`src/components/overlay/UnifiedOverlayWindow.vue:3-17`）——切换模式时整窗换色。组件 `<style>` 里另有 **18 种硬编码 hex**（`#ffd9a5`×4、`#f3b460`×3、`#fff6ee`×2、`#f7ecdf`×2、`#fff4e6`×2 …），构成一套与 `main.css` 灰阶完全不同的暖色板。

**分裂 ②：两套设计语言**

| | 首页 / 记录集 / 设置 | 剪切板 / 生词本 |
| --- | --- | --- |
| 页头 | 居中大标题（`clamp(1.75rem,5vw,2.5rem)` 渐变字） | 暖棕渐变 hero 卡 + 英文 kicker + 统计块 |
| 正文底色 | 冷灰 `#111113` / `#18181b` | 暖黑/暖棕 `#1f1711` / `#2d231b` |
| 强调色 | `#c9a227` | `#ffc557` / `#f3b460` |
| 信息密度 | 大留白、卡片内空 | 紧凑、信息块 + pill 标签 |

**分裂 ③：五套字体栈，子窗口字体实际不加载**

| 文件 | 字体栈 | 是否真的加载 |
| --- | --- | --- |
| `src/styles/main.css:7,50-51` | `@import` Google Fonts → `Instrument Sans` / `Space Mono` | ✅ 有网时加载（**离线桌面应用会静默回退**） |
| `src/styles/floating.css:23` | `Inter`, Segoe UI, … | ❌ `Inter` 从未加载 |
| `src/styles/selection-toolbar.css:7` | `Inter`, Segoe UI | ❌ |
| `src/styles/unified-overlay.css:12` | Segoe UI, PingFang SC, … | ✅（系统字体） |
| `src/styles/clipboard-overlay.css:26` | Segoe UI, PingFang SC, … | ✅ |

结论：主窗口用 Instrument Sans，悬浮层用 Segoe UI，`Inter` 是纯粹的死字体名。**同一个应用在不同窗口里字形都不同**，这是"看起来不协调"最直接的技术原因。

### 2.4 美化方案（三步，可执行）

#### 第一步：单一令牌文件（收益最大，一次解决"不协调"）

新建 `src/styles/tokens.css`，由 5 个入口共用（现在只有 `src/main.js:4-5` 引样式），并**删除**各窗口私有 `:root`：

```css
:root {
  /* 三级色阶：底 → 面 → 卡 → 抬升 */
  --bg-base:#0b0b0d; --bg-surface:#141417; --bg-card:#1a1a1f; --bg-raise:#232329; --bg-hover:#2c2c33;
  --line:#2a2a31; --line-strong:#3a3a43;

  --text-1:#f2f2f4; --text-2:#a9a9b3; --text-3:#7c7c87;
  /* 唯一强调色（金）+ 反色文字 */
  --accent:#c9a227; --accent-hi:#dcb63a; --accent-ink:#1a1400; --accent-soft:rgba(201,162,39,.14);
  /* 语义色唯一来源 */
  --ok:#4ade80; --warn:#f5a524; --err:#f87171; --info:#60a5fa;
  /* 间距 8 基数 / 圆角 4 级 / 字号 7 级 */
  --s-1:4px; --s-2:8px; --s-3:12px; --s-4:16px; --s-6:24px; --s-8:32px;
  --r-sm:8px; --r-md:12px; --r-lg:16px; --r-full:999px;

  /* 阴影 3 级 + 描边高光（替代 16 处手写 box-shadow） */
```

配套动作：

#### 第二步：统一页面骨架与原语

1. **`<PageHeader>`**：首页补页头，剪切板/生词本去掉自造 hero 卡改用统一页头，H1 尺寸一次拉齐；
2. **`<Button>`**：`variant(solid|outline|ghost|danger) × size(sm|md)`，替换约 30 种按钮写法；
3. **`<Input>/<Select>`**：合并 8 套输入框（统一宽度、统一高度、统一 focus 环）——直接解决设置页控件宽度不齐、文字截断的问题；

### 3.5 存储方案：JSON 优先、可迁移（替代数据库的全部机制）

> 前提约束：**不使用任何数据库**。以下 8 项机制合起来可以覆盖原本需要 DB 才能解决的问题。

**核心原则：单个 JSON 文件是唯一真相源；任何索引、清单、缓存都是派生物，删掉不影响数据完整性。**

#### ① 落盘：唯一入口 + 原子写

```python
# app/repositories/json_store.py
async def write_json_atomic(path: Path, data: dict) -> None:
    """原子写 JSON：先写同目录临时文件，再 os.replace 覆盖。"""
    tmp = path.with_suffix(path.suffix + ".tmp")
    async with aiofiles.open(tmp, "w", encoding="utf-8") as f:
        await f.write(json.dumps(data, ensure_ascii=False, indent=2))
    os.replace(tmp, path)   # Windows 同卷内是原子操作
```

- **保留现在的格式**（`indent=2, ensure_ascii=False`）：文件可读、可手改、可 git diff、可直接拷走 —— 这是"方便迁移"的物理基础，不要为了性能改成紧凑格式。
- 全仓只允许 `json_store.write_json_atomic()` 一个落盘点，禁止再出现 `open(path, 'w')`。

#### ② 并发：进程内锁 + 单写者约束

- 每个资源一个 `asyncio.Lock`（records / clipboard / wordbook / sessions / settings），串行化「读-改-写」序列。
- **跨进程用"单写者"约束，而不是分布式锁**：启动时在 `data/.writer.lock` 写入 `{pid, host, started_at, port}`；若锁文件存在且对应 PID 仍存活 → 拒绝启动并给出明确提示。
  - 这一条直接解决当前 **Docker 容器与原生应用共用同一个 `data/`** 的双写风险（报告 §4.5 问题 20）。
  - 如果确实需要两个进程共存，用成熟的 `filelock` 库做真正的文件互斥（**不要自己造轮子**），而不是靠"约定"。

#### ③ 正确性：版本号 + 乐观锁（替代事务）

- 每条记录/剪贴板项加 `revision: int` 与 `updated_at`；写路径：读当前 → 比对请求携带的 `revision` → 一致才原子写 `revision+1`，不一致返回 **409 Conflict**。
- 效果：即使出现第二个写者，也只会产生**明确的冲突**，而不是现在这种**静默丢更新**。
- 向后兼容：老 JSON 没有 `revision` 字段时视为 `0`，不需要一次性改写 708 个文件。

#### ④ 性能：内存索引 + 可重建清单（替代数据库索引）

- `RecordIndex` / `ClipboardIndex`：进程启动后**惰性**装载一次元数据（`id / created_at / status / is_favorite / title / 摘要前 N 字`），常驻内存；`GET /records`、搜索、分页全部走索引。
- 写入时 write-through 更新索引；用 `os.scandir` + 目录 `mtime`/文件数 做增量刷新（目录未变则跳过重扫）。
- 冷启动想更快时，落一份**派生清单** `data/.index/records.json`：内容 100% 可由源文件重建，**删掉无损**，并在 `.gitignore` 中忽略。这份清单承担了"数据库索引"的角色，但它是纯 JSON、可丢弃。
- 剪贴板 353 条、记录 708 条的正文总量很小，正文也可以一并进索引，搜索就不必读盘。

#### ⑤ 分页与搜索：基于索引，取消人为上限

- `/records?cursor=&limit=` 走索引排序分页，去掉现在 `limit=100` 的硬上限（708 条只能看到 100 条，报告 §5.1）。
- 搜索先用索引做标题/时间/状态过滤，再按需读命中文件做正文精确匹配。

#### ⑥ 数据卫生：用「文件侧 housekeeping」替代 retention job

启动时 + 每日一次 `housekeeping`：

| 动作 | 对应现在的问题 |
| --- | --- |
| 删除无主图片（`clipboard/images/` 中未被任何条目引用的 PNG） | 37 张孤儿图片 |
| 删除已合并会话的段文件 | 85 个残留段文件 |
| 把超过 N 小时仍为 `recording` / `optimizing` / `transcribing` 的对象标记为 `failed` 并记录原因 | 4 个卡死 6 个月的会话、2 条卡在 `optimizing` 的记录 |
| 日志 rotation（`RotatingFileHandler`） | `logs/app.log` 无上限 |

#### ⑦ 迁移工具：把"方便迁移"从口号变成能力

新增 `scripts/migrate_data.py` + `docs/数据目录结构.md`：

| 能力 | 说明 |
| --- | --- |
| 布局版本化 | `data/.schema_version` 记录布局版本，脚本据此决定是否迁移 |
| 平铺 ↔ 分片互转 | 现在是 `records/<id>.json` 平铺（708 个文件尚可）；单目录超过约 2 万文件时切到 `records/<yyyy>/<mm>/<id>.json`，脚本支持双向转换 |
| 校验 | 全量 JSON 可解析 + 记录数与索引一致 + 音频引用可达（现在 `757 wav ∩ 708 id = 0`，正好用这个脚本体检） |
| 压缩/美化 | `--compact` / `--pretty` 互转 |
| 导出/归档 | `--export out.zip`、`--archive 2026-09`：导出的 zip 解压即是可直接使用的 `data/` |

#### ⑧ 明确不做的三件事

- ❌ 不引入 SQLite / DuckDB / LMDB 等任何嵌入式数据库（即使"只是索引"）。
- ❌ 不引入需要常驻服务进程的存储（Redis/Postgres 等）。
- ❌ 不把二进制序列化（pickle/msgpack）作为持久格式 —— 会破坏可读性与迁移性。

#### 这套方案的代价（如实说明）

| 代价 | 缓解 |
| --- | --- |
| 跨进程并发能力弱 | 用"单写者锁"约束 + 版本号冲突检测，把静默丢数据变成明确报错 |
| 没有事务，多文件操作非原子 | 关键操作做成"单文件单次写入"；跨文件场景（合并会话）用 `revision` + 重试 + 启动时收敛 |
| 每次修改重写整份文件（写放大） | 单条记录体积小，可接受；真要优化可用 ⑦ 的分片布局降低单目录压力 |
| 索引与源文件可能不一致 | 索引是可丢弃派生物：启动时校验数量，不一致就整份重建 |

**什么时候需要重新评估这个决策**：单目录文件数超过约 5 万、或必须支持多进程/多机同时写入。到那时也应优先考虑"分片 + 单写者"，而不是直接上数据库。
