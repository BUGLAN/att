## 一、这是什么项目

面向中文语音输入场景的 Windows 桌面转写工具，技术栈为 **Electron + Vue 3 + FastAPI**，同时覆盖四条业务链路：

| 链路 | 内容 |
| --- | --- |
| 录音 | 全局热键（本地 Python desktop agent 监听）、单段/多段/流式三种模式、录音期间系统静音 |

| 文本优化 | 多 Provider LLM（DeepSeek/Claude/OpenAI/豆包/千问/自定义），提示词预设来自 `prompts/*.txt` |
| 桌面增强 | 剪贴板历史与悬浮窗、统一悬浮层（划词面板 + 剪贴板面板）、生词本、AI 划词动作（翻译/解释/总结/改写） |

## 六、缺陷清单（按严重度）

### 6.1 🔴 严重：两个已实测确认的安全缺陷

#### (1) 任意文件读取 —— 已实测确认可利用

`POST /api/clipboard/items` 接受任意 `metadata`（`app/clipboard/routes.py:25` 无字段校验），图片路径直接进 `Path()`（`app/clipboard/manager.py:106`），绝对路径会覆盖前缀目录，读取时 `FileResponse` 原样返回（`app/clipboard/routes.py:99`）。

**实测结果：**

```
POST /api/clipboard/items  {"item_type":"image","metadata":{"image_path":"E:\\repo\\att\\tmp\\probe_secret.txt"}}
GET  /api/clipboard/items/{id}/image
→ HTTP 200, bytes=26, body = "TOP-SECRET-PROBE-CONTENT"
```

即：任何能访问该后端的进程/网页，都能读取后端进程有权限读取的**任意文件** —— 包括 `.env`（内含真实 DeepSeek API Key）、`data/.encryption_key`、日志。

#### (2) CORS 通配 + 零鉴权 —— 已实测确认

`app/main.py:126-132`：

```python
allow_origins=["*"],
allow_credentials=True,     # 与 "*" 组合是非法规格用法，Starlette 会回显具体 Origin
```

**实测结果：**

```
GET /api/records  (Origin: https://evil.example)
→ Access-Control-Allow-Origin: https://evil.example
→ Access-Control-Allow-Credentials: true
```

后端**全程无鉴权**。虽然 Electron 只绑 `127.0.0.1`（`electron/python/manager.js:101-126`）且端口动态分配，但用户浏览器里任何一个网页都可以跨域读取 `/api/records`、`/api/clipboard/items`、`/api/settings`，并与缺陷 (1) 组合读取本地任意文件。另外 `python -m app.main` 的开发入口绑的是 `0.0.0.0:8000`（`app/main.py:171-174`），会直接暴露到局域网。

> 附带说明：这两条是我独立复现的。审计中还报告了"`DELETE /api/records/{id}` 可用 `%5C` 穿越删除任意 `*.json`"（Windows 反斜杠被 pathlib 当分隔符，`data/records/..\..\tmp\x.json` 可逃出目录）。**我实测未能确认**：用 `tmp/` 下的非 Record 结构探针发起删除，返回 500 且探针文件未被删除 —— 与"路径确实穿越到了目标，但因 JSON 结构校验失败而报 500"的解释一致，但不足以证明可删除。建议按"需修复"处理，但请勿当作已确认漏洞。

### 6.2 🔴 严重：所有 JSON 持久化都是"零锁 + 原地截断写"

- 四个 manager（records / clipboard / wordbook / session）**没有任何锁**（全 `app/` 仅 2 处 `Lock`，都在 `app/services/`）。
- 全仓库 grep `os.replace|os.rename|tempfile|NamedTemporaryFile` → **0 命中**，所有写入都是 `open(path, 'w')` 原地截断。

### 6.3 🟠 中高：录音状态机的"永久锁死"路径

`src/composables/useRecorder.js`（实际 **1898** 行）是应用最核心也最脆弱的文件。核心设计问题一句话概括：

> **副作用先置位，善后代码在会抛异常的 `await` 之后。**

`prepareRecordingEnvironment()` 先把 `startPending = true`、`appStore.setRecording(true)`、`floatingSessionActive = true`、悬浮窗切到 `recording`（`useRecorder.js:479-487`），**然后**才 `await getUserMedia()`（`:497-501`）；而三种模式的三处 `try/finally` 都在**它外面**（`:1127/1135`、`:1242/1250`、`:1299/1309`），该函数自身也没有 try/catch。

由此产生三条独立的"录音彻底不可用，只能重启应用"路径：

1. **麦克风权限被拒 / 无设备** → `getUserMedia` 抛出，`startPending` 与 `isRecording` 永久为真 → 热键守卫（`:1840-1842`）与手动按钮守卫（`:1387-1394`）双双静默 return；点"结束录音"只置一个永远不会被消费的 `pendingStopAfterStart` 标志（`:1416-1419`）。
2. **流式模式启动窗口期松键** → `cleanupStreamingSocket()` 先摘掉所有 handler 再 close（`:177-187`），导致 `:1146` 的 `await connectStreamingSocket()` **永不 settle** → `finally { startPending = false }`（`:1182-1184`）永不执行。UI 看似回到 idle 并弹一句"流式连接已断开"，但此后所有输入被吞。
3. **流式中途服务端断开** → `onclose`（`:682-688`）只改内部状态，不复位录音状态/时钟/托盘/悬浮窗 → 麦克风继续采集、时长无限增长、悬浮窗永久置顶显示"正在完成 Qwen 真流式转写"。

另外两条相关缺陷：

- **多段最后一片上传失败 → 永不合并**：`:933-947` 的 `uploadSessionSegment` 没有 catch，异常沿 `recorder.onstop`（`:564-567`，平台回调无人 await）变成 unhandled rejection，导致 `maybeFinalizeRealtimeSession()`（`:1090`）永不执行 → UI 永久"正在转写"，后端 session 与音频文件泄漏。
- **多段收尾只由 WebSocket 事件驱动**：`:959` 的三个守卫依赖 `realtimePendingSegmentIds` 被 WS 事件清空；全局 WS 掉线（后端重启）即永久卡住，无超时、无降级轮询。

## 八、看起来"像是半成品"但其实是有意为之的部分

为避免误判，以下是我判定为**有意设计**、但仍有风险的项：

- `/api/prompts` 只读 —— `file_manager.py` 顶部 docstring 明写 "backed only by prompts/*.txt files"，前端也已把编辑弹窗改成只读查看（`PresetEditModal.vue`）。
- Windows 不支持本地 vLLM 真流式 —— `app/stt/providers/qwen_asr_provider.py:113-122` 显式返回原因，不是漏写。
- AI 输出非 JSON 时降级为 `answer` 文本 —— `app/ai_actions/service.py:96` 有明确的 warning 日志。
- `PUT /api/settings` 静默丢弃未知键 —— 只有"全部非法"才 400，属有意的宽松策略（但拼错键时无任何提示，风险明确）。
- 后端不在启动时全量载入 JSON —— `initialize()` 只 mkdir，静态内存占用很小，这是个正确的选择。
