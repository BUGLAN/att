### 1. 统一浮层无入口；另有一批功能只有接口、没有界面入口

**浮层的证据链**（均已实测）：

| 可能的入口 | 实际情况 |
| --- | --- |
| 渲染进程调 `overlay.openClipboard/openSelection` | `src/composables/useElectron.js:108-126` 只有**定义**，`src/` 内零调用点 |
| WebSocket 命令 `clipboard_overlay_command` | `src/App.vue:108` 在 Electron 下直接 `return`；且 `app/**/*.py` 里**已无发送方** |
| 剪贴板捕获后自动弹出 | `electron/main.js:305` 的 `notifyClipboardChanged` 只发 `clipboard:changed` + `notifyDataChanged`，不打开窗口 |
| 托盘菜单 | `electron/tray/index.js:157` 只有「设置 / 退出」（另有记录列表项） |
| 全局快捷键 | `electron/main.js` 内**没有任何 `globalShortcut.register`** |
| 桌面代理 | `electron/desktopAgent/manager.js:173-194` 只转发 `hotkey.press/release`（录音用） |

`openSelection(...)` 的调用方，未补替代入口，而新浮层照旧交付。

**会导致什么**（现在就会发生）：

- **剪贴板面板 / 划词面板完全打不开**：托盘、全局快捷键、复制后自动弹三条路都没有入口，
  用户找不到任何打开方式，功能等于不存在；设置页那 4 个开关
  （`clipboard_overlay_retrigger_action`、`clipboard_overlay_enter_behavior`、
  `clipboard_overlay_auto_focus_search`、`clipboard_overlay_close_on_click_copy`）
  改了没有任何可见效果。
- **连带整条划词链路失效**：划词翻译不可达，而它是生词本的**唯一**写入来源 →
  **生词本永远是空的**；解释 / 总结 / 改写连封装都没有调用方。
- **半死状态的维护成本**：浮层窗口、IPC 通道、组件、样式、`unified-overlay.html`
  仍在被启动与打包（白占内存与包体），后来者容易误以为它在工作。
- 数据本身没坏：剪贴板历史、记录、生词本文件都照常写入，只是"看不到 / 进不去"。

**建议**：二选一，别停在半死状态。
(a) 补入口：托盘菜单项 / 第二个全局热键 / `ClipboardMonitor.onCaptured` 后自动弹；
(b) 彻底下线：连带删除 `electron/overlay/**`、`src/components/overlay/**`、
`src/unified-overlay.js|html`、`src/styles/unified-overlay.css` 与 6 个 `overlay:*` IPC 通道。

### 2. `--win` 打包必然失败，且打包产物缺 `scripts/`

**证据**：

- `electron-builder.yml` 的 `win.target` 同时声明 `nsis` 与 `portable`；
- `release/` 下只有 `win-unpacked`，**没有任何 Setup*.exe**；
  `tmp/package-nsis-retry.log` 末尾：`npx electron-builder --win nsis exited with code 4294967295`；
- `release/win-unpacked/resources/` = `app / app.asar / prompts / python / …`，**没有 `scripts`**；
  而后端 `app/services/qwen_streaming_service_manager.py:100,166` 会启动
  `uvicorn scripts.qwen_streaming_service:app`，`_project_root` 在打包态正是 `resources/`；
- `scripts/package-electron.js` 的 `verifyPackagedResources()` 自检**没有覆盖 `scripts/`**。

**会导致什么**：

- **拿不到安装包**：`node scripts/package-electron.js --win` 在 nsis 阶段以退出码 `-1`
  结束，`release/` 里只有免安装目录；打包脚本把它当整体失败，容易被误判成"打包坏了"
  而放弃出包（实际 `win-unpacked` 是可用的）。
- **打包版里 Qwen 流式录音不可用**：后端要 spawn
  `uvicorn scripts.qwen_streaming_service:app`，而 `resources/` 下没有 `scripts/` →
  进程起不来，用户在打包版选"流式 + Qwen"只会拿到报错；只有配远端
  `QWEN_STREAMING_BASE_URL` 能绕开，本地桥接在打包版无解。
- **自检形同虚设**：`verifyPackagedResources()` 不检查 `scripts/`，所以"能打包成功、
  一装就废"这类问题不会在本地或 CI 暴露，直到用户装上才发现。

**建议**：`win.target` 先收敛为 `portable`（或在文档明确"当前不产出 NSIS 安装器"）；
`extraResources` 增加 `scripts/`；`verifyPackagedResources()` 补一条存在性断言。

### 3. 多段录音「最后一片上传失败 → 永不合并」，且收尾没有超时降级

**证据**：

- `src/composables/useRecorder.js:599` 的 `recorder.onstop = async () => { … await onStop(blob) }`
  **没有 try/catch**，而浏览器不会 await 事件回调；
- `uploadRealtimeSegment()`（同文件 `:958-976`）只有 `try/finally`、**没有 catch**；
- 收尾只在 `maybeFinalizeRealtimeSession()`（`:1058`，由 `:1115` 触发）里执行 →
  上传抛错后这条路径永不执行，UI 永久停在"正在转写"，后端 session 与音频文件泄漏；
- 多段收尾依赖 WS 事件清空 `realtimePendingSegmentIds`（`:1541`、`:1572`）；
  全局 WS **确有固定 3s 重连**（`src/composables/useWebSocket.js:111` 的 `scheduleGlobalReconnect`，
  由 `onclose` 触发，另有 30s 心跳），但**无退避、无重试上限，且 `onerror` 不触发重连**；
  收尾本身也没有超时降级 → 后端长时间不可用时仍会卡住。

**会导致什么**（现在就会发生）：

- **触发条件很常见**：任一片上传失败即可——网络抖动、后端重启或超时、后端 500、磁盘写满。
- **录音界面彻底卡死**：UI 永久停在"正在转写"，录音按钮不可用，**后续录音也无法开始**，
  只能重启应用。
- **这段录音实际丢了**：收尾（合并分段 → 建记录）永不执行，用户以为录到了，记录库里却没有；
  同时 `data/audio/temp` 的分片与后端流式会话被泄漏（占空间与句柄）。
- **重连救不了它**：全局 WS 只做固定 3s 重连（无退避、无上限、`onerror` 不触发），
  而收尾只由 WS 事件驱动、没有超时降级，所以后端长时间不可用时照样卡住。

**建议**：`onstop` 包 try/catch（失败也要走收尾并提示）；给 `finalizeRealtimeSession` 加
超时兜底；给全局 WS 的重连加退避与上限。

## 🟠 中等

### 4. LLM provider 未设置请求超时

`app/llm/providers/openai.py:17`、`claude.py:17`、`deepseek.py:17`、`doubao.py`、`qwen.py`
构造客户端时都没传 `timeout`，SDK 默认 600s；全仓唯一的 `timeout=60.0` 在
`app/llm/optimizer.py:170`（旧的直连 DeepSeek 路径，已被 provider 抽象绕过）。
**会导致什么**：

- LLM 侧"连接建立后不回包"（代理挂住、网络黑洞）时，优化请求要**挂最多 10 分钟**才失败；
  界面一直转圈，用户只能强杀应用。
- 优化是串行的：开着"转写后自动优化"时，记录会长时间停在 `optimizing`，
  后续录音的优化排队等待。
- 用户无法区分"卡死"与"在等超时"，排障时容易误判成应用死锁。

**建议**：各 provider 统一注入超时（如 60s），并让 LLM 配置可覆盖。

### 5. 音频文件名与 `record.id` 完全错位（实测）

- `app/api/routers/records.py:104` 先生成一个 uuid 作为 wav 文件名，
  `record_manager.create_record()` 内部再生成一个 uuid 作为 `record.id`（`app/records/manager.py:72` 不接受外部 id）；
- 实测：`data/records` **719** 条记录、`data/audio/records` **768** 个 wav，**文件名交集为 0**；
- 后果：`get_audio_file_path(record.id)` 对所有记录都算错（当前唯一调用点是流式会话，
  它用 session_id 自成闭环，所以没爆）；另有 **13 条记录的 `audio_path` 指向不存在的文件**。

**会导致什么**：

- 当前功能上还没爆（唯一调用点用 session_id 自成闭环），属于**埋雷**：任何"按
  `record.id` 找音频"的新功能（音频导出、数据迁移、清理）都会拿不到文件。
- 已实测的 **13 条记录 `audio_path` 指向不存在的文件** → 在记录库里对这些记录
  回放 / 导出音频会 404 或报错。
- 直接挡住 §6 的音频清理：无法安全判断"哪个 wav 没有对应记录"，手工删就容易误删在用的音频。

**建议**：`create_record()` 支持传入 id，或统一用 record.id 命名音频；顺手修复那 13 条坏记录。

### 6. 音频没有 retention，磁盘只涨不降（实测）

`data/` 当前 **505MB**，其中 `data/audio` **464MB**（768 个 wav）。
`app/repositories/housekeeping.py` 只扫四类：孤儿图片 / 孤儿分段 / 卡死会话 / 卡死记录，
**不处理音频文件**；且启动期只做 dry-run（`app/main.py:100`），真正清理要手动
`scripts/housekeeping.py --apply`。
**会导致什么**：

- `data/` **只涨不降**（实测 505MB，其中音频 464MB / 768 个 wav），按现有录音量持续增长，
  最终撑满磁盘；届时后端写 JSON 与音频都会失败（表现为录音丢失、记录写不进去）。
- 没有任何界面入口能清理，用户只能手工进目录删文件——而手工删又受 §5 命名错位影响，
  容易删到仍在被引用的音频。

**建议**：增加"无对应记录的音频"清理类别（注意 §5 的命名错位，先修命名再按 id 匹配）。

### 7. 转写失败不写 `Record.error`

`app/services/transcription_service.py:152-170` 的失败分支只 `update_record(status=FAILED)`
+ WS 广播；而优化失败路径（`:145`）与 `records.py:333` 都会写 `set_error_message`。
`Record.error` 字段与 `from_dict` 兼容都是为此设计的，用户重启后却看不到转写失败原因。
**会导致什么**：

- 重启应用后用户只看到记录是"失败"，**没有任何原因**，无法区分是没网、密钥失效、
  音频损坏还是模型没开，只能反复重试猜原因。
- 同一界面里行为不一致：优化失败会写原因（`records.py:333`），转写失败不写，
  用户会以为"转写失败就是没救"。

**建议**：失败分支补 `set_error_message(record_id, str(e))`。

### 8. 存储层 4 处静默吞异常（无日志）

`app/clipboard/manager.py:237`、`:308`、`app/wordbook/manager.py:80`、`:220` 均为
`except Exception: continue`，而 `app/records/manager.py:119` 同类循环至少有 `logger.error`。
后果是"数据损坏"变成"数据不存在"，用户与日志都看不到。
**会导致什么**：

- 单条 JSON 损坏（半截写、手工编辑出错、磁盘错误）会让这条数据**凭空消失**：
  列表里查不到、日志里也没有痕迹 → 用户认为"数据被应用吃了"，且无法自查。
- 排查只能人工翻 `data/` 目录比对文件数，成本极高；这类"静默跳过"正是历史报告中
  "数据静默丢失"一类的残留。

**建议**：补 `logger.warning(..., path=..., error=...)`，控制流不变。

### 9. LLM 配置加载「全有或全无」

`app/llm/config_manager.py:49-62` 在循环里直接 `LLMConfig(**config_data)`，
单条坏配置会让整个循环中断（外层只 log 一句），后续配置全部丢失，
`_default_config_id` 可能为 None → 优化静默退化为"未配置"。
**会导致什么**：

- 只要**一条**配置不合法（旧字段类型、手工编辑出错），循环就中断，后面的 LLM 配置
  全部不加载 → 设置页 LLM 列表变空、默认配置丢失、"自动优化"静默不可用。
- 用户视角是"我配的 LLM 全没了"，而文件其实还在 `data/llm_configs.json` 里，
  容易在界面上重复添加或覆盖掉。

**建议**：逐条 try/except，坏条目跳过并告警；加载 0 条时提升为启动期告警。

### 10. `MAX_UPLOAD_SIZE` 半失效 + 4 个环境变量完全空转

- 读取限流用 `settings.max_upload_size`（`records.py:95`、`sessions.py:79`），
  但 `app/audio/processor.py:72` 的校验用**硬编码** `MAX_FILE_SIZE = 500MB` →
  把 env 调到 800MB 仍会在 500MB 被拒；
- `supported_formats` / `chunk_duration` / `target_sample_rate` / `target_channels`
  在 `app/config.py` 有字段但**零读取**，真实生效的是 `AudioProcessor` 的类常量。

**会导致什么**：

- 把 `MAX_UPLOAD_SIZE` 调大（例如 800MB）后，500MB～新上限之间的文件仍被拒，
  而且报的是 **400「格式/时长非法」**而不是 413 超限 → 用户以为文件损坏，
  实际是硬编码的 500MB 在拦。
- 改 `SUPPORTED_FORMATS` 加新格式、改 `CHUNK_DURATION` / `TARGET_SAMPLE_RATE` /
