# 多段录音问题报告

## 1. 问题概述

当前 Electron 应用中的多段录音模式已经具备基础可用性，但整体稳定性和转写质量仍然明显低于单段录音模式。

现阶段最突出的问题包括：

- 多段录音切段过碎，导致 Whisper 输入片段过短。
- 部分片段会出现明显幻听文本，例如：`中文字幕由 Amara.org 社群提供`、`MING PAO CANADA // MING PAO TORONTO`。
- 短句在多段模式下更容易识别错误。
- 多段实时文本存在顺序错乱、失败后卡住、阶段状态不一致等问题。
- 优化链路本身也存在编码和 prompt 配置异常，短句进入优化时更容易被“改坏”。

结论：

当前多段模式的问题不是单点故障，而是由“切段策略 + 片段时长 + Whisper 输入质量 + 结果拼接 + 优化配置异常”共同导致的。

## 2. 当前已观察到的现象

### 2.1 转写阶段出现固定幻听文本

已在历史数据中确认，以下文本并不是只出现在优化结果里，而是在原始转写结果中就已经出现：

- `中文字幕由 Amara.org 社群提供`
- `MING PAO CANADA // MING PAO TORONTO`

这说明问题首先发生在 ASR 转写阶段，而不是 LLM 优化阶段。

### 2.2 短句更容易出问题

短句、停顿频繁、边界不清晰的输入，更容易出现：

- 整句被截断
- 片段内容不足
- 幻听公共字幕尾注
- 标点和词序异常

### 2.3 多段模式下实时展示不稳定

已观察到以下风险：

- 片段异步完成时，前端可能按返回顺序拼接，而不是按真实 sequence 拼接。
- 某个片段失败时，前端等待状态可能无法正确收尾。
- 悬浮窗和主界面在多段模式下的信息一致性仍不稳定。

### 2.4 优化阶段对短句不稳定

当前设置里虽然 `auto_optimize` 大多时候是关闭的，但一旦开启，短句很容易被过度改写或补充说明。

根因不是“短句天然不能优化”，而是当前 prompt / preset 体系本身存在编码异常，短文本在信息量不足时更容易被坏 prompt 放大问题。

## 3. 已确认的疑似问题点

### 3.1 切段策略过于激进

问题描述：

- 当前多段模式依赖前端静音检测切段。
- 一旦检测到静音，就可能立刻 stop 当前 segment。
- 如果用户只是短暂停顿思考，并不代表这一句真的结束。

可能后果：

- 片段被切得很碎。
- Whisper 输入上下文不足。
- 句首句尾容易丢字。
- 短片段更容易出现幻听。

涉及位置：

- `src/composables/useSilenceDetector.js`
- `src/composables/useRecorder.js`

### 3.2 缺少前滚缓冲 / 后滚缓冲

问题描述：

- 当前切段逻辑基本依赖“检测到说话开始后再录”“检测到静音后再停”。
- 这会导致句首和句尾边界非常脆弱。

可能后果：

- 开头的第一个字被吃掉。
- 句尾收得过短，语义残缺。
- Whisper 拿到的信息不完整，识别质量下降。

涉及位置：

- `src/composables/useSilenceDetector.js`
- `src/composables/useRecorder.js`

### 3.3 Whisper 片段过短，容易产生幻听

问题描述：

- Whisper 对极短、极碎、低信息量的片段稳定性很差。
- 这类片段常见表现就是生成公共字幕尾注、网站署名、模板化短语。

已观察到的典型幻听：

- `中文字幕由 Amara.org 社群提供`
- `MING PAO CANADA // MING PAO TORONTO`

结论：

这不是优化器杜撰出来的文本，而是 ASR 对坏片段的典型 hallucination。

涉及位置：

- `app/stt/transcriber.py`
- `app/api/routes.py`
- `data/records/*.json`
- `data/sessions/*.json`

### 3.4 前后双重 VAD 可能造成二次裁切

问题描述：

- 前端已经通过静音检测做了一次切段。
- 后端 Whisper 默认配置仍启用了 `vad_filter`。

可能后果：

- 片段边界被二次裁切。
- 句首句尾进一步被压缩。
- 原本勉强够长的 segment 又被裁成低信息量片段。

当前状态：

- 这部分已经尝试在 session segment 转写时关闭后端 `vad_filter`。
- 但整体质量问题仍未彻底解决，说明这只是原因之一，不是全部原因。

涉及位置：

- `app/stt/transcriber.py`
- `app/api/routes.py`

### 3.5 实时片段拼接缺少稳定顺序控制

问题描述：

- 多段转写是异步完成的，不同 segment 返回顺序可能与上传顺序不同。
- 如果前端直接按消息到达顺序拼接，就会出现内容错位。

可能后果：

- 实时文本顺序混乱。
- 用户误以为模型识别错了，实际上是拼接错了。

涉及位置：

- `src/composables/useRecorder.js`
- `app/api/routes.py`

### 3.6 片段失败后的状态回收不完整

问题描述：

- 某个 segment 转写失败后，如果前端仍然把它视为 pending，会导致 finalize 等待状态异常。

可能后果：

- 多段录音结束后卡住。
- session merge 迟迟不触发。
- UI 状态和实际后台状态不一致。

涉及位置：

- `app/api/routes.py`
- `src/composables/useRecorder.js`

### 3.7 优化 prompt / preset 存在编码异常

问题描述：

- 当前优化器默认 prompt 存在乱码。
- `prompts/` 目录内的内置模板大多也存在乱码。
- `settings.json` 和 `presets.json` 中的 preset id 也已经出现编码损坏。

可能后果：

- 长文本仍可能勉强工作。
- 短句信息量低时，LLM 更容易被坏 prompt 带偏。
- 出现无意义扩写、解释性补充、格式异常等问题。

涉及位置：

- `app/llm/optimizer.py`
- `app/prompts/manager.py`
- `prompts/*.txt`
- `data/settings.json`
- `data/prompts/presets.json`

### 3.8 主界面和悬浮窗仍处于“实验性联动”

问题描述：

- 多段模式新增后，主界面、悬浮窗、托盘状态之间尚未完全抽象为统一状态机。
- 目前更多是“能工作”的联动，而不是“严格一致”的状态派生。

可能后果：

- 某些边界场景下 UI 表现不统一。
- 用户会看到“正在录音 / 正在转写 / 正在监听”切换不够自然。

涉及位置：

- `src/composables/useRecorder.js`
- `src/components/home/RecorderSection.vue`
- `src/components/floating/FloatingWindow.vue`

## 4. 初步修复方向

### 4.1 第一优先级：先修多段 ASR 输入质量

目标：

- 让 Whisper 拿到的 segment 更长、更完整、更像一句完整的话。

建议措施：

1. 保留最短片段时长限制。
2. 静音到来时，若当前片段过短，不立即切段，而是继续并入下一句。
3. 增加前滚缓冲和后滚缓冲。
4. 保留最长片段上限，避免重新退化成超长整段。

建议参数：

- `min_segment_duration`: `2.0s ~ 2.5s`
- `max_segment_duration`: `8s ~ 12s`
- `pre_roll`: `300ms ~ 500ms`
- `post_roll`: `200ms ~ 300ms`

### 4.2 第二优先级：增加幻听垃圾文本拦截

目标：

- 对典型公共字幕尾注和无意义模板文本进行过滤。

建议措施：

1. 在 segment 转写完成后增加一层轻量规则过滤。
2. 对已知高频垃圾文本建立黑名单。
3. 若片段文本命中黑名单且长度很短，则直接丢弃，不参与 merge。

建议首批黑名单样式：

- `中文字幕由 Amara.org 社群提供`
- `MING PAO CANADA`
- `MING PAO TORONTO`
- 其他后续从真实数据中继续补充

说明：

这不是根治方案，但能立刻降低用户可见的脏结果。

### 4.3 第三优先级：修复实时拼接和失败收尾

目标：

- 提高 session 收尾稳定性和实时文本可读性。

建议措施：

1. 所有 `segment_transcribed` 结果按 `sequence` 排序后再展示。
2. 所有 `segment_failed` 必须从 pending 集合中清理。
3. finalize 逻辑增加超时兜底，避免某个 segment 永远不返回时整场卡死。

### 4.4 第四优先级：修复优化链路编码问题

目标：

- 避免短句在优化阶段被错误 prompt 放大问题。

建议措施：

1. 修复 `app/llm/optimizer.py` 中的默认 prompt 编码。
2. 修复 `prompts/*.txt` 中所有内置模板编码。
3. 修复 `data/settings.json` 和 `data/prompts/presets.json` 中损坏的 preset id。
4. 给短句增加保护策略：
   - 文本过短时不优化。
   - 或仅做轻量标点修正，不做重写。

### 4.5 第五优先级：统一多段模式状态机

目标：

- 降低主界面、悬浮窗、托盘之间的状态不一致。

建议措施：

引入统一 session 状态源，例如：

- `idle`
- `listening`
- `speaking`
- `segment_processing`
- `finalizing`
- `completed`
- `error`

然后由这个状态源统一派生：

- 主界面状态
- 悬浮窗状态
- 托盘状态

## 5. 建议的实施顺序

建议不要并行大改，按下面顺序推进：

### 阶段 1：先保质量

- 收紧切段策略
- 增加最短时长和缓冲
- 降低超短片段进入 Whisper 的概率

### 阶段 2：再保稳定

- 处理 `segment_failed`
- 处理实时拼接顺序
- 增加 finalize 兜底

### 阶段 3：再保体验

- 悬浮窗滚动展示前序片段
- 主界面与悬浮窗状态统一
- 调整多段模式提示文案

### 阶段 4：最后修优化链路

- 修正 prompt / preset 编码
- 给短句加优化豁免策略

## 6. 当前判断

### 结论 1

`中文字幕由 Amara.org 社群提供` 这类问题，主因是多段 ASR 输入质量差，不是 AI 优化阶段凭空生成。

### 结论 2

“短句更容易坏”是合理现象，因为：

- 片段更短
- 上下文更少
- 边界更容易被裁坏
- Whisper 更容易幻听
- LLM 在坏 prompt 下更容易过拟合短文本

### 结论 3

当前多段模式仍应视为“实验性功能”，不宜直接作为稳定主路径替代单段模式。

### 结论 4

最值得优先投入的不是继续做更多 UI，而是先把“切段质量”和“片段质量”稳定下来。

## 7. 建议的下一步

如果继续推进，建议直接进入下面这个最小闭环：

1. 完成前滚 / 后滚缓冲。
2. 增加短片段垃圾文本过滤。
3. 给 finalize 增加失败兜底。
4. 修复优化 prompt 和 presets 编码。

等这四步完成后，再决定是否继续增强悬浮窗和主界面实时体验。
