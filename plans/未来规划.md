# 未来规划

## 1. 当前判断

这个项目不应该只停留在“实时语音转文字”。

更有价值的方向是把它升级为一层通用的 AI 内容操作层，让用户能够在不同软件、不同场景下，用自然语言直接处理当前内容，而不是频繁复制、切换窗口、粘贴到其他 AI 工具里再搬回来。

核心链路应从：

`语音输入 -> 转文字 -> 输出结果`

逐步升级为：

`获取上下文 -> 理解意图 -> AI 处理 -> 结构化输出/回写/分发`

## 2. 产品定位

未来更适合的定位不是“转写工具”，而是：

- 语音驱动的内容操作层
- 跨应用的 AI 文本变换器
- 面向内容处理工作流的受控 Agent

重点不是让模型“回答问题”，而是让系统“帮用户完成一次内容处理动作”。

例如：

- 把当前选中文本整理成 Markdown
- 把会议记录提取为待办事项
- 把一段草稿改成正式邮件
- 把当前内容总结后回写到原处

## 3. 核心机会

### 3.1 替代碎片化 AI 工作流

当前大量 AI 使用场景都很割裂：

1. 复制内容
2. 切换到 AI 工具
3. 粘贴内容
4. 输入需求
5. 复制结果
6. 再贴回原来的地方

如果系统能把这条链路压缩为一次操作，价值会非常直接。

### 3.2 从“输入工具”升级为“结构化处理入口”

未来重要的不只是把人说的话转成文字，而是把人的意图转成结构化对象和动作。

例如最终产物不只是 text，还可能是：

- task
- summary
- markdown
- meeting note
- reply draft
- checklist
- structured record

## 4. 高频使用人群与场景

### 4.1 程序员

高频需求主要集中在技术内容处理：

- 解释报错和日志
- 翻译英文文档并保留术语
- 从讨论记录中提取待办和风险
- 把改动说明整理为 commit message 或 PR 描述
- 给代码片段加注释、解释逻辑
- 把散乱表述整理成清晰的技术说明

高频命令示例：

- 解释这个报错并给排查步骤
- 翻译并保留术语
- 提取待办和风险点
- 整理成 PR 描述
- 给这段代码加注释

### 4.2 小说作者

高频需求主要集中在文本创作与风格控制：

- 把零散灵感整理成提纲
- 润色段落
- 调整角色口吻
- 从片段扩写成完整场景
- 检查设定冲突
- 压缩冗长内容、增强节奏
- 回顾前文并总结人物状态

高频命令示例：

- 整理成剧情提纲
- 润色得更有画面感
- 改成更符合角色口吻
- 扩写成完整场景
- 检查与前文设定是否冲突

### 4.3 文员 / 普通办公人员

高频需求最稳定，也最容易形成长期习惯：

- 把内容整理成正式通知
- 把散乱文字整理为会议纪要
- 从聊天记录中提取重点与行动项
- 将长文压缩成汇报要点
- 把草稿改成礼貌、专业的邮件或消息
- 把内容整理成规范格式或 Markdown

高频命令示例：

- 整理成正式通知
- 整理成会议纪要
- 提取待办事项
- 压缩成 5 条汇报要点
- 改写成礼貌专业的邮件

## 5. 最值得优先沉淀的命令集

跨人群最通用、最容易高频使用的命令包括：

- 整理成规范格式
- 转成 Markdown
- 总结核心要点
- 提取待办事项
- 改写得更正式
- 改写得更简洁
- 翻译并保留原意
- 整理成会议纪要
- 生成回复/邮件草稿
- 解释这段内容是什么意思

这些命令比开放式自由对话更适合作为第一批产品能力，因为输出目标更明确、质量更稳定。

## 6. 可行边界

### 6.1 不能把目标设成“整合所有软件的全部上下文”

这在技术上并不现实，原因包括：

- 软件生态割裂
- 系统权限限制
- 受保护输入框和私有应用难以读取
- 跨应用上下文一致性难以维护

### 6.2 正确目标是“统一高频上下文入口”

真正值得先整合的是：

- 当前选中文本
- 剪贴板文本
- 语音指令
- 本地历史记录
- 当前活动窗口标题
- 简单 OCR 内容

这已经足以覆盖大量高频场景。

### 6.3 深度集成应该是选择性地做

后续如果要扩展，可以挑少量高价值软件做深度适配，而不是试图一次性兼容全部软件。

优先级更高的集成对象可能包括：

- 浏览器
- VS Code
- Word / WPS
- Notion / 飞书
- 企业沟通工具

## 7. 为什么需要额外交互

如果系统只是“拿到一段文本就发请求”，它只能完成浅层能力：

- 简单转写
- 单次润色
- 单次总结

一旦目标变成 Agent，就必须知道：

- 当前处理对象是什么
- 用户具体想做什么
- 输出要回到哪里
- 当前这一步属于哪种工作流

因此必须增加轻量但结构化的交互层，为 Agent 提供任务信号，而不是让模型完全靠猜。

这层交互不一定是完整聊天框，更适合是一个任务面板，至少要明确：

- 输入来源：选区 / 剪贴板 / 历史记录
- 操作命令：整理 / 总结 / 提取 / 改写 / 翻译
- 补充说明：一句自然语言
- 输出方式：替换 / 插入 / 复制 / 保存

## 8. Agent 化判断

当前如果系统只是：

- 获取文本
- 拼 Prompt
- 发给模型
- 返回结果

那它仍然只是一个 AI 请求层。

但未来如果要完成真正的内容处理工作流，它就必须具备以下能力：

- 获取上下文
- 理解用户意图
- 选择命令和处理策略
- 调用工具
- 执行回写或分发动作

因此它未来应逐步从“请求层”演化为“受控型 Agent”。

这里的 Agent 不是全自动、无边界的通用代理，而是：

`面向内容处理工作流的受控 Agent`

强调：

- 用户明确发起
- Agent 在清晰边界内工作
- Agent 使用有限而可靠的工具
- Agent 以完成内容操作为目标，而不是自由聊天

## 9. 适合的演进路径

### 第一阶段：请求层

- 基础语音转写
- 基础文本改写
- 单轮 AI 调用

### 第二阶段：命令层

- 把自然语言归一到稳定命令
- 形成一批高频命令模板

### 第三阶段：工作流层

- 根据命令走不同处理流程
- 明确输入来源与输出目标
- 支持回写、复制、保存

### 第四阶段：Agent 层

- 上下文感知
- 工具调用
- 多步执行
- 轻量记忆
- 内容处理闭环

## 10. 现阶段结论

当前最重要的不是立刻写大而全的技术方案，而是确认方向：

1. 项目未来不应只做实时语音转文字。
2. 更大的机会在于“跨应用的内容处理层”。
3. 这层能力的核心不是聊天，而是内容操作。
4. 产品必须围绕高频场景，而不是追求全上下文。
5. 要从 AI 请求层逐步演化为面向工作流的受控 Agent。

## 11. 下一步建议

后续可以继续往下拆两类内容：

- 哪些高频场景最值得优先做成产品能力
- 最小需要增加哪些交互，才能让 Agent 真正稳定工作

这两部分明确后，再进入具体产品方案和技术架构会更稳。
